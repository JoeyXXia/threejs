# Day40 — Runner 与 Socket 的故障窗口

日期：2026-11-28（Asia/Shanghai）；本地与 GitHub `main` 开工基线 `1fcf629eb83edf2d44c1df3c408c2e01e9bffb31`。Day39 的路径和多车种子验收已归档。此前已有单 runner/双连接接管、API 进程被杀、权限变化、回放和游标测试，本轮补真正的数据库中断及浏览器同步故障链。

## 两组可独立审查的改动

1. **T11 数据库故障**：`scripts/day40-database-outage.mjs` 接入默认集成入口，在真实取货事务已写入但提交前停掉临时 PostgreSQL。两条连接分别尝试读取并推进。数据库恢复后比较余额、任务、审计、事件、回放帧与检查点，确认第二 runner 接管，旧提案被拒绝，原任务继续。
2. **T12/T14 浏览器故障**：`scripts/browser-checks/day40-fault-matrix.js` 使用隔离的 Chrome、真实 NestJS / PostgreSQL / Socket.IO。改动通知传输而非业务结果：重复与漏掉通知，延迟真实快照，浏览器上下文断网，注入 410 验证全量重订阅。另切跨空间的 B 仓，释放 A 的迟到响应，测试实际会话撤销和历史拒绝。详见 [Day40 验收](../../reports/day-40-acceptance.md)。

## 权威与风险

只有 PostgreSQL 已提交的 checkpoint、库存流水和事件序号是权威。应用层失去 PostgreSQL 不能继续确认运动，也不能以一条 Socket 通知直接改库存。最易发生误判的是把提交前事务读到的取货当真，或在切仓后让较早的请求回填新仓。验收分别跨独立连接读数据，并核对 B 仓真实水位和预占。没有增加生产故障开关或依赖；不部署、不推进 Day41、不改 PDF。
