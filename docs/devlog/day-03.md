# Day 03：布局、货位与库存基础

实际日期：2026-11-01（Asia/Shanghai）。基线 Git：`66edbd1`。这是接续的 Day 3，不按日历补造中间开发记录。

## 目标与结果

新增版本化布局、稳定货位、SKU/批次、余额和不可修改的流水；期初数据从合成 fixture 通过事务写入；API 返回真实布局和库存。结果见 [验收报告](../../reports/day-03-acceptance.md)。

实际查询每仓：布局 v1、30×20、6 区域、2 货架、17 货位、2 SKU、2 批次、11 余额、11 期初流水。现存 62 件，预占 0，样本未过期时 available 55、HOLD 7。两个空间的演示仓库彼此隔离。

## 可独立审查的改动

1. **模型/约束**：稳定 Location 与 LayoutLocation 分离；数量 CHECK、scope/SKU-batch 复合外键；发布布局不可改、服务格校验、整位容量及单 SKU/批次约束；流水 append-only。
2. **数据/API**：自行编写的合成 v1；稳定 ID 和期初业务键；余额/流水同事务 seed；受授权的 layout/inventory 只读接口，无库存写入接口。
3. **验证/报告**：流水重算 CLI、26 项 Day 3 专项测试 + 18 项 Day 2 回归、数据库重启核对、开发库增量升级、ADR/README/报告。

没有新增框架或依赖；没有实现前端库存页、R3F、寻路/调度、业务收发货、预占命令或队列。前端只修正了“尚无库存”的过时说明。

- `pnpm db:generate`、`pnpm check` 通过。
- `pnpm test:integration`：真实 PostgreSQL 18.6、2 个 suite、44 项测试通过，0 失败。测试后关闭并重启 DB，再对全部余额重算，0 差异。
- Day 2 开发库原先只有 identity 迁移；增量部署两条 Day 3 迁移，seed 后原 4 个用户及凭据保持、仓库名称/版本保持；新增总计 22 余额、22 流水。
- `pnpm reconcile`：consistent=true，mismatches=[]。
- `pnpm smoke --dev-api --with-auth`：API/Vite 代理、登录、读取身份、退出、旧令牌拒绝均通过。

地图版本 v1；无模拟 seed 或运行 tick，因为今天没有模拟器。固定身份/布局数据不是随机模拟结果。

## 关键反例

- 阴性测试直接向 DB 写负数、超预占、超容量、跨批/SKU、跨仓关联，确认拒绝且记录未被改坏。
- 两个真实连接同时争抢同一空储位、分别写入不同质量行的 25 件，只成功一条；最终没有超出容量 40。测试清理临时余额后重算仍一致。
- 修改未发布布局使服务点落货架/越界、货位越区、货架重叠，发布失败；已发布位置、容量和身份直接更新也失败。
- 一笔测试用完整转移记录可同时重算来源和目标，库内总量保持 62；测试事务最终回滚，不把它当作已实现运输业务。
- 强制期初流水插入失败，验证新仓库、布局、余额、流水全部回滚。
- 故意把 HOLD 余额 7 改成 8、再删掉，重算分别发现 actual=8/expected=7、actual=0/expected=7，最后回滚。

## 失败与学习

第一次开发库升级检查执行早于便携数据库就绪，连接失败；等到明确 ready 后重试成功，没有用失败结果填通过。首次测试只覆盖已发现的 18 项旧测试，补齐专项后先通过 41 项，再加入转移/期初回滚/批次到期三项，最终完整复验 44 项；只以最终输出作为本次总结果。

AI 完成模型、代码、测试和报告初稿；用户尚未独立审查或口述，不替用户宣称已掌握。建议独立解释：为什么货位 ID 不等于 mesh/坐标；为什么货架中的位置需要地面 serviceCell；为什么按所有质量行求容量；为什么对账必须 FULL OUTER JOIN 且在同一快照中进行。
