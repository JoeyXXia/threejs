# ADR 0005：入库收货、批次与质检的原子边界

日期：2026-11-05。状态：采用。接续 `6b8c5e7 / v0.1-scene`，只实现 Day 8。

## 最小业务模型

一单一个已有 SKU、一个批次、一个当前发布布局内的 QC 货位、正整数件数；全量收货一次、全量质检一次。不做部分收货、拆单、质检撤销、SKU 管理、运输、预占、Socket 或后台队列。

状态为 `CREATED → RECEIVED → PASSED / REJECTED`。入库单保存创建/收货/质检操作者、时间、原因、数量、批次、QC 货位和版本。首版不另建质检表，以不可重复阶段和单据结果表达一次质检。

批次新增可空 producedAt，沿用 expiresAt；UTC ISO 时间由服务端严格校验，拒绝不存在的日历日期、未来生产日期和生产日期不早于到期时间。相同 SKU/批次编码的日期必须一致，不能用新入库单覆盖旧批次日期。过期批次可以收进 HOLD，放行时再次按服务端时间检查，过期只能拒绝并保持隔离。页面日期按 UTC 零点提交，到期日零点起不可放行，不解释为本地当日末尾。

## 状态权威与事务

PostgreSQL 是单据、批次、余额、流水、审计和幂等结果的权威。每条写命令使用同一个 Prisma 交互事务：

1. 对访问记录加共享锁并查询当前权限；admin/operator 可写，viewer 拒绝，身份来自认证会话。
2. 锁 Warehouse 行，之后锁 InboundOrder，再锁 QC Location，固定顺序与既有容量触发器的 Warehouse→Location 顺序兼容。
3. 检查当前阶段、QC 放置、SKU/批次归属、日期和容量；改变业务状态。
4. 同事务写流水、AuditLog 和成功的 IdempotencyRecord，全部提交或全部回滚。

使用当前仓库行作为粗粒度串行入口；尚无 runtime/runner，不提前引入新锁表。事务内没有 HTTP、相机操作或外部消息。小样例下便于验证，未测试吞吐，也不宣称支持高并发多仓部署。权限变更使用现有访问记录锁协调，返回历史幂等响应前也必须重新授权。

## 数量与流水

| 命令 | 余额变化 | 流水 | 全仓现存 |
| --- | --- | --- | --- |
| 创建单据 | 无 | 无；审计记录创建 | 不变 |
| 收货 q | QC/HOLD 增 q | RECEIPT，外部→QC/HOLD | 增 q |
| 质检通过 q | 同位 HOLD 减 q、RELEASED 增 q | TRANSFER，同位置不同质量 | 不变 |
| 质检拒绝 | 不改变余额 | 无数量流水；审计记录拒绝 | 不变 |

质检只转换该单 quantity，绝不把整个 QC 余额放行。多个单据及 seed 可共享同 SKU/批次的 HOLD 余额，但各单据独立推进；当前没有外部调整、预占或搬运命令改变这些单据的数量归属，未来加入时必须继续设计分配/冻结边界。通过时先减 HOLD 再增 RELEASED，避免容量触发器看到事务中的临时超容；剩余为零的余额行保留，方便账本复算。

收货阶段流水业务键 `inbound:<orderId>:receipt`，放行业务键 `inbound:<orderId>:release`。唯一约束加阶段检查，防止换 key、换操作者重复过账。拒绝的唯一性由单据阶段检查和事务行锁保护。沿用完整来源/目标流水和现有 FULL OUTER JOIN 对账，无需建立另一套账本。

## 幂等与响应丢失

复用 `(spaceId, warehouseId, actorId, operation, key)` 唯一范围。服务端按固定字段顺序、修剪后的文本与规范化日期计算 SHA-256；同 key 同参数返回已提交的历史响应，同 key 不同参数返回 409。操作类型与目标单据均进入命令身份或 hash，跨单不能误重放。只有成功结果与业务一起持久化，失败回滚后允许同 key 重试，当前不自动删除成功记录。

前端保存当前未确认命令的参数指纹和随机 key，同页面、原参数重试继续用该 key；成功后清除。刷新/卸载不持久化未确认创建请求，用户应先读取单据确认结果，不保证跨刷新继续重放创建。对既有单据的收货/质检，即使丢掉前端 key，服务端阶段仍会拒绝重复处理。HTTP 取消/超时不表示后端事务回滚，UI 明确提示结果不确定及核对方式。

## API 与前端同步

前缀 `/spaces/:spaceId/warehouses/:warehouseId/inbound-orders`：GET 列表和表单选择项，POST 创建，POST `:orderId/receive`，POST `:orderId/inspect`。浏览器通过 `/api` 代理；请求体只接收允许字段，不接受 actor/scope 注入。列表读使用 RepeatableRead，最多返回最近 100 单并提供 hasMore，未实现完整分页。

Query key 为用户/空间/仓库，结果经共享 schema 与归属校验；Zustand 不存单据或库存。写成功后精确 invalidate 当前入库 key 与 warehouse-snapshot key，不做乐观数量更新。页面重新读取确认结果；外部修改仍需手动刷新。切仓/退出卸载页面并中止 fetch，迟到写响应不得重建旧缓存；401 清会话和查询缓存。R3F/2D 继续复用同一库存快照，无动画决定过账。

## 数据迁移与验证边界

新增两条迁移：先提交 MovementKind.RECEIPT 枚举值，再添加入库表、批次日期和 CHECK，避免在同一迁移事务中使用未提交的新枚举值。不修改既有已发布迁移，不 reset 数据库。期初 OPENING 的语义和 seed 数量不变。

真实集成使用一个临时 PostgreSQL 集群中的两个独立库：原 `warehouse_twin_test` 保留旧 44 项固定样例，`warehouse_twin_inbound_test` 运行新增 20 项写入测试。两库都迁移、seed，并在集群重启后分别全量对账；没有用调整旧断言掩盖夹具串扰。开发库未执行迁移，已有开发数据升级前需按 README 运行 db:migrate；本次没有声称已验证生产升级或部署。
