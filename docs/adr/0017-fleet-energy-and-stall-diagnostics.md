# ADR0017：车队电量预算、单容量充电与无进展诊断

日期：2026-11-19。范围：Day26 网格化软件车队，旧单车行为不变。

## 电量和接单

电量整数 0–10000（基点）。每个确认空载步消耗 1，载货移动步消耗 2；等待、装卸和未确认的提案不耗电。接单预算为「取货前路线步数 + 2×载货路线步数 + 卸货后到充电位的空载步数 + 20」。这些是模型常量，不是硬件测量。回充路线只作准入估算，不预订目标或未来通行权。

优先按 Day23 CHARGING 资源定义的首格选一个代表充电位；无此类资源则用布局 CHARGING 服务点。最多检查按曼哈顿距离排前四的候选；每条 A* 至多 2000 扩展、10ms。封锁/货架是硬障碍，几何规划不假定充电位能立即腾空。任一必要路线无解/超预算或电量不足时拒绝，写事务无运输新预占、无新 claim；原出库分配预占并非此次接单所创建。原有已提交 claim 的同参查询语义不改变。

## 充电与事务

`POST .../fleet/charge` 接受 robotId、START/STOP 和 reason；仅写授权用户可提交。只允许无活动运输、无设备故障、非 ERROR 的空载车开始，不允许已计划车并行接单。模式写入可选 `WarehouseRuntime.fleet.state.robots[].charge`，旧 JSON 默认为无计划。布局、路径和电量均按 PostgreSQL 最后确认检查点计算，事务内按原 ACL SHARE → Warehouse/runtime 加锁，核对版本/tick/布局，原子写状态和 `FLEET_CHARGE`（操作人、原因、tick、目标）。旧 runner 提案经原 owner/epoch/版本门禁不能提交。

去充电位的步进照常经过保守顶点/边和资源仲裁。配置组持有唯一物理 owner，默认单格则直接使用顶点占格。只有到位后，每个确认 tick 增加 250 基点，到满电自动清活动计划，不移车、不释放实际占格；STOP 同样不挪车。电量恰好到零的车只可在已到位时充电，不凭空跨格。已有活跃充电路径不能被新封锁跨断，先 STOP 再封锁；布局变化时不继续提交旧充电路径。充电授权在接收命令时检查，不设独立充电用户租约。

## 诊断与边界

改道后副作用前再次检查 LOADING/TRANSPORT 是否有足够电量跑完剩余载货段并留正电量；不足则停步，保留 task、TRANSIT 和目标容量，提示 ENERGY_LOW。不自动载货回充、转货或跨车救援。可由新的可行路线解除；无可行路线则保持并提示人工介入。

连续 20 个提交等待 tick 产生 NO_PROGRESS，成功步进或显式控制清连续等待。状态快照每车至多一个当前诊断，优先设备故障、低电量、持续无进展。键使用车辆、claim 或充电目标及类别；设备故障加入起始 tick。FLEET_TICK 仅写相对前一快照新出现的键，持续等待不重复发出；设备故障首次仍由既有 FLEET_FAULT 记录。诊断在消失后可再次出现，不视作永久全局唯一事件。没有新队列、通知服务或指标采集。Query 轮询，R3F 插值仍只消费已确认位置。

单容量保安全，不保活性：满电停车仍可能堵下一辆；操作员应安排普通可行搬运离开或停止后续计划，不能把占格自动清掉。无公平性/死锁解决保证、无真实耗电/实时 SLA、无 Day27 进程退出验收。
