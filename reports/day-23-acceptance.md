## 实现与安全边界

在原 PostgreSQL fleet JSON 中持久配置 1–32 组、每组 1–128 格单容量 AISLE/PARKING/CHARGING/WORKSTATION，无新迁移或依赖。许可与位置、库存效果、claim、tick 和事件同事务。旧 JSON 无资源保持兼容；先配置再运行，已有占格自动归其车，不允许用改配置、完成任务或进程租约超时清掉物理占用。

纯反例覆盖不同空入口争同组、owner 出清、下一 tick 转交、空闲/错误/完成驻留、优先级/等待、非法几何、不可重置和 JSON 恢复。真实库增加授权配置、批次回滚、接管/撤权保留、正常离开与完成驻站、故意损坏的只读对账检测。没有真实工业控制、动态重规划、自动充电、产品级恢复或无死锁保证。

## 已发现并修正的问题

- 第一轮纯测试发现：先做顶点仲裁会让累计等待更久但没有资源许可的外车抢赢目标，合法 owner 反而停住。改为先过滤无许可目标（其车仍留原地占格），再做物理冲突判断；原失败用例不改成“永远等待”，仍验证 owner 正常出清和下一车进入。
- 初次类型检查暴露 exactOptionalPropertyTypes 与 Zod optional 输出不一致；明确旧字段可缺失/undefined，不绕过检查点解析。
- 首轮新库用例中测试误用 `layoutPlacement`（实际 Prisma 模型是 `layoutLocation`），并把超出契约 511 范围的格预期为 409；修正夹具名，分别断言格式越界 400、地图越界 409。首轮失败不算通过，须重新完整执行。
- 第二轮接管夹具复用了 Day22 故意销毁的 runner，`prepare` 正确返回 null；改为新的独立 runner，保持旧测试的 graceful destroy 语义，不修改产品使已销毁进程重新启动。最终须再次完整复验。配置在仓库锁后重新读当前布局，避免锁等待期间旧授权读取的布局被替换。
