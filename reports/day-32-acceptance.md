## API 与可用历史

- `GET /spaces/:spaceId/warehouses/:warehouseId/history?from=<UTC ISO>&to=<UTC ISO>&limit=50`：指定最多 24 小时的定位窗，最多返回 100 条事件。选取不晚于 `from` 的最近记录帧；如果此前没有帧，则尝试范围内首帧。没有可定位记录时明确返回空结果。返回 `first` 为目标起始帧序号、`baseline` 为不晚于它的最近基线、`through` 为该查询末尾事件序号。读取最后帧后的可见业务事件不会凭空生成新帧。
- 续页发送同样的时间参数及上一页的 `after=nextAfter&through=through`，直到 `nextAfter=null`。从基线按连续 seq 提供事件；成功 tick 的重复大 payload 换成紧凑 frame，任务/封路等非 tick 事件保留原 payload。发现缺段返回 409，不编造库存、位姿或布局。每页基线会重复，消费者按 seq 去重。
- `GET /spaces/:spaceId/warehouses/:warehouseId/history/layouts/:layoutId`：只读该仓留档布局；当前仓库的登录与读取权限每次重查。静态几何来自历史布局，动态导航/资源定义来自基线与后续事件，全车位置、占位 owner、阶段和载荷来自记录帧。
- 库存保存的是 tick 提交事务内全仓摘要（现存、预占、可用、待检），不是逐批逐货位历史；帧间以事件描述变化。历史的时间标签是数据库事务时间，不是精确发布或客户端接收时间。现阶段未配置自动清理，未测长期存储成本或写入性能。

## 实测

- 构建、类型与 lint 检查通过；Vite 仍提示部分分包超过 500 kB，本日未测性能。单测 137 项（核心 55、Web 82）通过。本日无前端交互改动，使用真实 Nest HTTP 和 PostgreSQL 验证接口。
- 单车完成一趟实际搬运，捕获 47 帧，基线为 tick 1、20、40。首次在途帧为 tick 27，仓库摘要为现存 62、预占 1、可用 54、待检 7。发布布局 v2 后仍能加载 v1；v2 在 tick 48 留下首个基线。最后一个旧 tick 后的仓库重命名仍出现在历史事件中，没有虚构运动帧。
- 三车分页样本，基线 seq 6、固定上界 seq 20，每页最多 2 条，拼接 14 条连续事件和 10 条后续轨迹帧。期间有新 tick 提交，续页上界不变。由基线、封路事件与归档帧复现的关闭格 (0,0)、revision 1 及三车位姿/阶段和原已提交数据一致；故障事件仍可读。跨仓返回 404，超范围/超页限返回 400。
- 注入 tick 事件失败及轨迹插入失败，验证库存、任务、检查点、审计、水位和帧数一同回滚；重试只增加一帧。原始验收 JSON 留在本地。
- 全量集成退出 0：Node 65 项、Jest 99 项，共 164 项。四个临时 PostgreSQL 库真实重启后对账通过；历史帧计数与按序内容摘要一致（合计 4,943 帧、274 个基线）。从旧 schema 应用新迁移后，既有业务行及凭据检查通过。Jest 对保留在本地输出目录的隔离工作树仍提示同名包，未影响测试结果。
