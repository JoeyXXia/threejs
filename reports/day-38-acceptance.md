# Day38 验收 — 真实 PostgreSQL 竞争矩阵

日期：2026-11-27（Asia/Shanghai），基线 `ccec1b1`。

## 可观察验收

1. **T02**：收货、取货、放货、发运的重复请求实际跨连接等待；每个逻辑动作只有一条流水，收货与发运净变化正确，只有一份日报待办。
2. **T03**：同批次来源库存、暂存剩余容量各一场竞争；失败方没有多占库存、半成品任务或空的在途库位。
3. **T04**：故障与预先计算的车队提案争抢；旧提案被拒绝，货物与原有效任务仍对应；解除故障只卸货一次。
4. **T05**：运输到暂存不扣全仓库存；提前发运不改状态。注入完整写入后的回滚，证明未提交状态未泄漏、跟随重试只扣一次。
5. **T06**：盘点先冻结和预占先提交两个顺序均覆盖；前者拒绝不足的分配、审批后可分配，后者阻止开盘覆盖已预占数量。

## 复验命令

```powershell
pnpm check
pnpm test:unit
$env:TEST_API_PORT_BASE='13040'  # 可选：避免 Windows 保留端口
pnpm test:integration
git diff --check
```

新增矩阵自身不依赖 Redis。可另设 `TEST_DISPATCH_REDIS=1` 一并跑 Day36/37 故障回归（需启动 Docker 引擎并预拉镜像）。逐轮数据写到本地 `reports/day38-wms-contention.json`（不提交）。种子为项目既有合成布局和初始库存，每场争抢建独立仓，UUID 用于隔离；顺序由提交屏障控制，非随机时序抽样。

## 实测结果

22:08（上海时间）隔离定向复验，5 个场景共跑 **20 轮**，数据库共确认 **36 个锁等待窗口**，没有将 JS Promise 重叠计为数据库竞争。测试环境为 Windows x64、Node 22.14.0、PostgreSQL 18.6；`pnpm check` 和 146 项单测（core 55、web 91）通过。

| 场景 | 实际轮数 | 已观测锁等待 | 核对的业务结果 |
| --- | ---: | ---: | --- |
| T02 重复过账 | 4 | 16 | 每轮 4 个逻辑动作各一条关联流水；收货 2、发运 1，现存 62→63，只有 1 条日报待办。 |
| T03 库存与容量 | 4 | 8 | 每轮同批次 25 件只由一个订单预占；独立暂存仓 99 + 1 预留达到容量 100，只有一个新任务与在途库位。 |
| T04 载货故障 | 4 | 4 | 每轮旧提案被拒；在途保留原归属及 1 件货，恢复后原任务到暂存，全仓现存 62。 |
| T05 发运回滚 | 4 | 4 | 每轮在途时拒绝发运，暂存时保持 62；注入发运事务回滚后无可见半成品，跟随事务只扣一次，到 61。 |
| T06 盘点与分配 | 4 | 4 | 盘点优先、分配优先各 2 轮。前者审批调整 +1 后正常预占；后者拒绝开盘，无盘点变更。 |

逐轮库存与预留对账一致，事件序号连续；不把复验轮数叠加为首次样本规模。

首轮全量中，新增 Day38 矩阵通过，既有 Day32 历史测试的一次封路返回 HTTP 409（原断言只记录了状态码）。该步骤在真实 runner 活动期间执行。测试夹具改为仅对明确的「重规划期间状态/布局变化」拒绝读取当前状态并有限重试，要求封路 revision 未变；其它拒绝仍立即失败，历史及封路断言不变。最终套件实测触发了 1 次该分支，随后成功封路并通过历史分页断言。

首轮显式开启的 2 条 Day36/37 Redis 故障用例因 Docker 引擎管道不可用而无法启动容器。此次不将其计为通过；后续按 Day38 范围运行 PostgreSQL 默认门禁，不启动或改动宿主 Docker 服务。

最终 `pnpm test:integration` 退出码 0：Node 73 项通过、2 项可选 Redis 故障用例跳过，Jest 99 项通过，合计 172 项。最终套件再次跑完同样的 20 轮、观察到 36 个锁等待。4 个隔离 PostgreSQL 测试库重启后对账一致；最终 `pnpm lint` 与 `git diff --check` 通过。Vite 仍有构建分块偏大提示，Jest 仍有既有本地嵌套工作树的同名包警告。

## 范围

直接调用真实 NestJS 服务而不是 HTTP；本矩阵不是压力测试、跨集群高可用或生产吞吐测量，也不声称覆盖所有数据库调度。回滚故障在测试包装的事务提交边界注入，不改生产代码。
